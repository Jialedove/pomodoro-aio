# Pomodoro AIO 重构目标书 v1

## 1. 重构目标

本次重构的目标不是继续扩展“普通专注”“循环工作”“长专注”等模式，而是**重新定义 Pomodoro AIO 的核心模型**：

> **Pomodoro AIO 是一个由「工作模块」与「休息模块」自由组合而成的循环执行器。**

用户可以自由添加、删除、排序工作与休息模块，并按照自己定义的顺序执行和循环。

在此基础上，可以**可选地开启「推进中的项目」功能**，用于把多个工作组织到项目之下，并汇总这些工作的番茄投入。项目系统与循环工作系统相互独立；关闭项目功能后，Pomodoro AIO 应当仍然是一款完整、简洁的循环工作工具。

最终要从：

```text
普通专注
循环工作
长专注
A / B
每 N 轮休息
共同项目
……
```

转变为：

```text
工作 / 休息模块
        ↓
自由组合
        ↓
顺序执行与循环

＋

可选的项目组织系统
```

---

# 2. 产品最终模型

整个系统划分为三个相互独立的层次：

```text
Pomodoro AIO
│
├── 模块层
│   ├── 工作模块
│   └── 休息模块
│
├── 编排层
│   ├── 模块顺序
│   ├── 下一模块
│   ├── 是否循环
│   ├── 循环次数
│   └── 自动 / 手动进入下一模块
│
└── 项目层（可选）
    ├── 推进中的项目
    ├── 工作与项目的关系
    └── 项目番茄汇总
```

三个层次分别回答三个问题：

| 层次  | 回答的问题            |
| --- | ---------------- |
| 模块层 | **这一段我要做什么？**    |
| 编排层 | **做完以后下一步是什么？**  |
| 项目层 | **这些工作总体在推进什么？** |

项目层不得参与计时序列本身。

---

# 3. 删除“模式”概念

重构完成之后，产品内部不再存在：

```text
普通专注模式
循环工作模式
长专注模式
```

也不再存在固定的：

```text
任务 A
任务 B
```

传统番茄工作法只是：

```text
工作 25 分钟
↓
休息 5 分钟
↓
循环
```

现在的双任务循环只是：

```text
工作 A
↓
工作 B
↓
循环
```

长专注只是：

```text
工作 50 分钟
```

因此这些都不需要单独的运行逻辑。

**一个统一的模块执行模型应该能够自然表达它们。**

---

# 4. 工作模块

工作模块代表一段真正的生产性活动。

例如：

```text
工作
────────────────
事情：视频生产流程的学习
时长：30 分钟
工作区：视频学习
执行时黑屏：否
```

工作模块至少应支持：

| 属性      | 含义                 |
| ------- | ------------------ |
| 名称 / 事情 | 当前具体要做什么           |
| 时长      | 本段持续时间             |
| 工作区     | 可选的 Workspace / 布局 |
| 黑屏      | 是否在执行期间进入黑屏        |
| 模块 ID   | 用于稳定识别该工作          |

工作模块完成后：

```text
产生有效工作时长
↓
折算 🍅
↓
写入当日日记
↓
更新工作统计
↓
如果启用项目系统，则同步项目统计
↓
进入下一模块
```

工作模块才产生番茄。

---

# 5. 休息模块

休息不是工作模块的一种特殊配置，而是一种明确的模块类型。

例如：

```text
休息
────────────────
类型：散步
时长：10 分钟
执行时黑屏：是
```

用户可以定义不同的休息方式：

```text
短暂休息
散步
闭眼
喝水
拉伸
离开电脑
自由活动
……
```

休息模块至少支持：

| 属性        | 含义        |
| --------- | --------- |
| 休息类型 / 名称 | 这一段准备如何休息 |
| 时长        | 休息持续时间    |
| 黑屏        | 是否强制离开屏幕  |
| 模块 ID     | 用于稳定识别    |

休息模块：

```text
不产生 🍅
不增加工作次数
不写入任务工作量
```

但它仍然属于正式的运行阶段，应支持：

```text
开始
暂停
继续
恢复
异常恢复
黑屏
到点提醒
进入下一模块
```

也就是说：

> **休息不参与生产力记账，但参与执行状态机。**

---

# 6. 模块可以任意组合

模块数量不再限制为两个。

用户可以创建：

```text
工作
工作
休息
```

也可以：

```text
工作
休息
工作
工作
休息
```

甚至：

```text
工作
工作
工作
休息
```

模块应支持：

```text
新增
删除
编辑
拖动排序
```

编排器只根据列表顺序工作。

例如：

```text
① 阅读论文        30 min
② 写笔记          20 min
③ 散步            10 min
④ 编程实践        40 min
⑤ 闭眼休息         5 min
```

运行：

```text
1 → 2 → 3 → 4 → 5
```

如果开启循环：

```text
1 → 2 → 3 → 4 → 5
↑                 ↓
└─────────────────┘
```

---

# 7. 删除特殊的循环休息规则

现有：

```text
完成 N 个 A→B 轮之后插入一次短休
```

这一功能不再保留。

因为它属于固定 A/B 架构产生的特殊补丁。

新的模块系统可以直接表达：

```text
A
B
A
B
A
B
休息
```

然后循环整个序列。

原则是：

> **能够通过模块组合表达的行为，不再增加特殊规则。**

因此新架构应逐步删除类似：

```text
cycleBreakEvery
A/B 特殊轮数判断
cycleRest 特殊分支
```

这样的领域概念。

---

# 8. 循环规则统一放到设置中

模块只描述模块自身。

它不应该负责：

```text
下一步去哪
执行几轮
是否自动进入下一段
```

这些由统一的循环设置控制。

第一阶段循环规则只需要支持：

```text
序列结束后
● 从头重新开始
○ 停止

模块结束后
● 等待确认
○ 自动开始下一模块

循环次数
● 无限
○ 一次
○ 指定 N 次
```

以后即使增加新的循环行为，也应该进入编排层，而不是污染 Work / Rest 模块。

---

# 9. UI 的核心目标：配置灵活，执行简单

这是这次重构最重要的交互目标之一。

## 编辑状态

用户看到完整循环：

```text
循环工作

① 工作
   视频生产流程学习
   30 分钟
   视频学习布局
   □ 黑屏

② 工作
   剪辑实践
   20 分钟
   剪辑布局
   □ 黑屏

③ 休息
   散步
   10 分钟
   ☑ 黑屏

［＋工作］ ［＋休息］
```

用户可以：

```text
增加模块
删除模块
修改模块
重新排序
```

---

## 执行状态

真正执行时，不应持续向用户暴露大量配置。

界面重点只显示：

```text
当前

工作
视频生产流程学习

29:42

下一项：
工作 · 剪辑实践 · 20 分钟

［暂停］
［完成本段］
```

必要时：

```text
展开完整循环
```

核心原则：

> **编辑阶段提供组合能力，执行阶段最大限度降低认知负担。**

---

# 10. “完成本段”与“完成事情”继续分离

必须区分两个概念。

### 完成本段

意味着：

```text
结束当前计时模块
结算已经产生的有效工作时长
进入下一模块
```

它并不代表事情已经完成。

例如：

```text
工作：写论文
```

今天可能连续执行十次。

---

### 完成事情

意味着：

```text
任务本身完成
↓
结算当前已经产生的工作量
↓
勾选日记任务
↓
从可选工作中移除 / 更新状态
```

所以：

> **模块完成 ≠ 任务完成。**

这一语义必须保留。

---

# 11. 番茄、工作段、循环次数分离

新的统计模型必须明确区分：

```text
🍅 工作量
工作模块完成数
休息模块完成数
完整循环数
```

例如：

```text
工作 30 min
休息 5 min
```

执行一次后：

```text
番茄：1.2🍅
工作：1 段
休息：1 段
循环：1 次
```

休息永远不能增加番茄数量。

循环次数也不能再与番茄数量混为一谈。

---

# 12. 项目系统成为独立、可选功能

项目功能不属于循环工作的必要组成部分。

因此新增设置：

```text
项目功能

☑ 启用“推进中的项目”
```

关闭时：

```text
循环工作 UI 正常运行
不显示项目 UI
不要求选择项目
不执行项目同步
不出现项目相关操作
```

这时 Pomodoro AIO 就是一款纯粹的：

> **模块化循环工作工具。**

开启后：

```text
出现“推进中的项目”独立 UI
启用工作与项目之间的关系
工作结算时可以同步项目番茄
```

项目系统必须是：

> **可插拔功能，而不是核心计时系统的依赖。**

---

# 13. 项目 UI 与循环工作 UI 隔离

不应继续把：

```text
共同项目
```

放在循环工作的主要操作区域。

建议至少在逻辑上存在两个独立视图：

```text
循环工作

推进中的项目
```

例如侧栏可以：

```text
番茄钟
├─ 循环工作 View
└─ 推进项目 View
```

或者通过不同入口打开。

---

# 14. 「推进中的项目」UI 的职责

项目页面主要回答：

> **我的这些工作分别在推进哪些项目？**

例如：

```text
推进中的项目

视频生产学习                    4.6🍅

关联工作
✓ 视频生产流程学习
✓ 剪辑练习
✓ 分镜实践

［打开项目］
```

另一个：

```text
NCB                             8.2🍅

关联工作
✓ 学习者状态实现
✓ Evidence Retrieval
✓ 修复 Agent 流程

［打开项目］
```

用户应当能够在这里：

```text
选择推进中的项目
把工作关联到项目
解除关联
查看该项目累计投入
打开项目笔记
```

第一阶段建议：

> **一个工作最多归属一个项目。**

先保持关系简单。

以后确有需求再升级为多项目关系。

---

# 15. 项目关系独立于循环顺序

这是架构上的重要约束。

例如循环是：

```text
工作 A
↓
休息
↓
工作 B
↓
工作 C
```

项目可能是：

```text
项目 X
├── A
└── C

项目 Y
└── B
```

因此不能把：

```text
projectId
```

理解为当前循环的“共同项目”。

应该理解为：

```text
workModule / task
        ↓
project relation
```

项目负责组织和汇总工作。

循环负责组织时间。

---

# 16. 项目关闭后的系统必须真正独立

如果：

```text
enableProjects = false
```

那么项目功能应该做到：

```text
不影响模块运行
不影响计时
不影响日记结算
不影响启动速度
不要求存在项目数据
不产生项目错误
```

也就是说不能出现：

```text
项目没配置，所以无法开始工作
```

这种耦合。

项目同步失败也不能影响工作番茄已经成功写入的结果。

这实际上延续了当前项目“附加同步”的正确方向。

---

# 17. 运行内核的目标模型

最终运行态应该围绕：

```text
“现在正在执行哪个模块”
```

来设计。

而不是：

```text
“现在属于 standard 还是 cycle”
“现在是 A 还是 B”
```

概念上趋向：

```js
runtime = {
  status,

  currentModuleId,
  currentModuleIndex,
  moduleRunId,

  durationMs,
  startedAtMs,
  elapsedMs,
  remainingMs,

  completedLoopCount,

  pendingSettlement
}
```

逐步移除：

```text
workMode
cycleSlot
cycleRoundCount
cycleBreakEvery
A/B 特殊状态
longFocus 特殊状态
```

具体实现过程中可为迁移暂时保留旧字段，但**新业务逻辑不得继续建立在这些概念之上。**

---

# 18. 每次执行必须产生执行快照

模块配置和正在执行的实例要分开。

假设用户启动：

```text
工作 A
30 分钟
黑屏
```

开始之后，即使用户随后编辑模块：

```text
改成 15 分钟
关闭黑屏
换任务
```

当前已经运行的这一段仍然应该按照启动时的快照执行。

所以需要：

```text
Module Definition
        ↓ start
Module Run Snapshot
```

执行快照至少固定：

```text
模块 ID
模块类型
名称 / 任务
计划时长
黑屏
工作区
开始时解析出的项目关系
```

这样可以避免运行中配置变化污染已经开始的工作结算。

---

# 19. 项目关系也应在工作开始时冻结

例如：

```text
工作 A
→ 项目 X
```

开始后用户把它改成：

```text
工作 A
→ 项目 Y
```

正在运行的这一段仍应计入：

```text
项目 X
```

下一次再执行 A 才计入 Y。

这样历史记录才能具有明确语义。

---

# 20. 现有可靠性机制应保留

本次是**领域模型与 UI 重构**，不是推翻已有的可靠性机制。

应继续保留：

```text
绝对时间计时
暂停 / 恢复
插件重载恢复
pending settlement
幂等结算
日记原子修改
项目失败重试
frontmatter 修复
session / run 唯一标识
```

新的模块系统建立在这些机制上。

不能因为架构变简单，就重新退化成：

```text
一个 setInterval + 到点直接写文件
```

---

# 21. 黑屏能力模块化

黑屏不再区分：

```text
普通专注黑屏
任务 A 黑屏
任务 B 黑屏
休息黑屏
```

而统一成：

```text
当前模块是否启用 blackout
```

也就是：

```text
Module
└── blackout: true / false
```

无论：

```text
工作
休息
```

都可以使用同一个黑屏服务。

黑屏只是当前执行模块的一项效果。

---

# 22. Workspace 同样属于模块效果

工作区切换也不应该继续绑定：

```text
cycleWorkspaceCommandA
cycleWorkspaceCommandB
```

而应该：

```text
WorkModule
└── workspace
```

以后休息如果也需要一个“休息布局”，结构同样能够支持，而不需要改变运行引擎。

---

# 23. 设置页的目标结构

设置页应该围绕真正的系统级行为，而不是单个 A/B 参数。

例如：

```text
循环行为
────────────────
模块完成后：
自动进入下一项 / 等待确认

序列结束后：
重新循环 / 停止

默认循环次数：
无限 / N 次


功能
────────────────
☑ 启用推进中的项目
☑ 启用通知
☑ 启用声音


数据
────────────────
当日日记路径
番茄字段
任务写入规则
……
```

而类似：

```text
任务 A 时间
任务 B 时间
循环几轮休息
长专注默认时间
```

都应从全局设置中消失。

因为它们已经属于模块配置。

---

# 24. 数据迁移目标

旧用户的数据应安全转换，但新产品不继续暴露旧概念。

迁移规则大致为：

```text
普通专注
→
工作
休息
```

```text
循环 A/B
→
工作 A
工作 B
```

如果旧配置存在：

```text
每 N 轮休息
```

迁移阶段可以将它展开为等价模块序列。

例如：

```text
每 3 轮休息
```

转成：

```text
A
B
A
B
A
B
休息
```

长专注配置迁移成：

```text
普通工作模块
duration = 原长专注时间
```

迁移后不继续维护“长专注模式”。

原则：

> **兼容旧数据，不兼容旧架构。**

---

# 25. 明确不做什么

为了避免再次发展成复杂工作流平台，本次重构明确不追求：

```text
任意图节点连线
条件判断节点
脚本节点
并行任务
复杂 if / else
自动 AI 调度整个序列
项目嵌套工作流
一个工作同时关联无限项目
复杂依赖图
```

Pomodoro AIO 仍然应该是：

> **一个非常简单的时间执行工具。**

它的灵活来自：

```text
工作 / 休息
+
任意排序
+
简单循环规则
```

而不是来自复杂的工作流引擎。

---

# 26. 重构完成后的理想用户体验

一个第一次打开插件的用户，可以直接创建：

```text
工作 25 分钟
休息 5 分钟
```

点击开始。

无需理解：

```text
普通模式
循环模式
A/B
长专注
休息频率
```

一个有自己工作方法的用户，可以创建：

```text
阅读 40
写笔记 20
散步 10
编程 50
闭眼 5
```

直接循环。

一个只需要循环工作的人，可以永久关闭：

```text
推进中的项目
```

产品不会因为缺少项目而增加任何复杂度。

而需要长期项目统计的用户，可以打开：

```text
推进中的项目
```

把：

```text
阅读
写作
剪辑
```

分别组织到对应项目中。

---

# 27. 验收标准

重构可以认为完成，至少需要满足以下结果：

1. 软件内部只有一种执行体系，不再区分普通模式和循环模式。

2. 用户可以添加任意数量的工作和休息模块，并自由调整顺序。

3. 工作模块产生番茄，休息模块永远不产生番茄。

4. 工作和休息都可以独立配置时长与黑屏。

5. 工作模块可以独立配置 Workspace。

6. 删除“A/B 每 N 轮插休息”的特殊逻辑。

7. 删除独立长专注模式。

8. 循环次数、序列结束行为、自动进入下一段等统一进入循环设置。

9. 编辑循环和运行循环在 UI 上有明显区别。

10. 运行状态重点显示当前模块和下一模块。

11. “完成本段”和“完成任务”语义保持分离。

12. 项目系统拥有独立 UI。

13. 项目系统可以在设置中完全关闭。

14. 项目关闭后，循环工作所有功能仍然完整可用。

15. 项目负责工作组织和番茄汇总，而不参与时间序列。

16. 项目同步错误不能破坏工作日记已经成功完成的结算。

17. A/B、standard/cycle、long-focus 等旧概念逐步从核心领域模型移除。

18. 原有可靠性机制、异常恢复、幂等结算继续有效。

# 28. 一句话重构目标

> **把 Pomodoro AIO 从“拥有多个专注模式的番茄钟”，重构为“一个由工作与休息模块自由组合的轻量循环执行器”；项目管理作为独立、可关闭的增强层，用来组织和汇总工作，而不增加核心循环的复杂度。**

如果再进一步压缩，这次重构真正要做到的是：

```text
自由组合，但不复杂。
统一架构，而不是增加模式。
项目可增强，但绝不成为依赖。
配置可以丰富，执行必须简单。
```
